# Armory Ledger contributor instructions

## Scope and required reading

- Work in `/opt/armory-ledger-dev`. Do not access or modify the separate production
  checkout `/opt/armory-ledger`, production configuration, or production data
  unless the user explicitly authorizes that specific scope.
- Before implementation, read [README.md](README.md), [SECURITY.md](SECURITY.md),
  [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), [docs/DECISIONS.md](docs/DECISIONS.md),
  [docs/IMPLEMENTATION_STATUS.md](docs/IMPLEMENTATION_STATUS.md), and
  [docs/ROADMAP.md](docs/ROADMAP.md), plus the applicable task instruction.
- For schema work, read [docs/v0.1.2-schema-plan.md](docs/v0.1.2-schema-plan.md)
  as historical context and inspect current models/revisions. Its original
  migration-existence statements are stale; the status document explains this.
- `instructions/` contains task specifications. Reading a pending task during
  documentation discovery does not authorize implementing it. Respect the active
  user request, especially documentation-only and read-only limits.
- Inspect Git status before changes. Preserve unrelated user work, untracked
  files, ignored deployment files, and existing documentation.

## Architecture and coding conventions

- FastAPI/Jinja monolith, synchronous SQLAlchemy/PostgreSQL, vanilla JavaScript
  and shared CSS. Do not introduce a frontend framework or background service
  without a task need and an approved scope change.
- Follow neighboring modules: typed SQLAlchemy `Mapped` models, UUID identifiers,
  Pydantic request validation, router dependencies, and explicit transaction
  handling. Most request schemas live in routers; announcements have a separate
  schema module. Firearm write logic currently lives in its router.
- Keep ownership filters in server queries and validate related-record ownership.
  Admin privileges never bypass private inventory isolation. Admin user views may
  show account identity fields, never another user's inventory or derived counts.
- Require Armory User at login; Armory Admin is additional signed-session authority.
  Keep server-side `/admin*` enforcement and CSRF checks for admin mutations.
- Manufacturers/calibers and ammo product definitions are shared. Avoid mutating
  shared product metadata when editing one owner's lot. Do not redesign reference
  ownership, add merge/admin editing, or infer caliber compatibility from names.
- Monetary values use Decimal/Numeric. Unknown price is NULL, distinct from zero;
  preserve recorded currency and plain decimal values in numeric inputs.
- Use timezone-aware timestamps; reject ambiguous announcement API timestamps.
  Preserve request-time announcement behavior without adding a scheduler/polling.
- Reuse base templates, partials, heritage rules, `record-back` and button classes.
  Render user text with escaping; do not turn announcements into raw HTML.
- A logical ammunition lot UUID is not a manufacturer lot-number string. Preserve
  transaction and range history when changing inventory behavior.

## Testing and verification

- No automated test suite, test framework configuration, or lint/build toolchain
  for frontend assets was found at the documentation baseline. Do not claim tests
  ran merely because syntax checks or a release health check passed.
- For new behavior, choose focused tests appropriate to the task and existing
  dependencies; document any new test setup. Do not add production-data fixtures.
- Use explicitly authorized disposable PostgreSQL for database-specific tests.
  Never run destructive or migration tests against development/production data
  by assuming a database URL is disposable.
- For static-only tasks, use source inspection, Python AST parsing (without app
  imports), template parsing, JavaScript syntax checks and `git diff --check` as
  appropriate. Avoid generated bytecode/cache files. Do not start the app merely
  to inspect it; settings/session initialization may require secrets or a DB.
- Check untracked new files too; ordinary `git diff` omits them. Report exact
  checks, results and limitations. Do not install dependencies or start services
  implicitly during a documentation-only task.

## Development, migration, and deployment precautions

- `.env`, local `compose.yaml`, and local release/rebuild helper scripts are
  ignored. Do not print secrets, commit instance settings, or overwrite them.
- The public Compose example pulls GHCR; local development Compose builds source
  and includes a tunnel. Verify the intended directory, Compose file, database
  and container target before any authorized operational command.
- `docker-entrypoint.sh` runs `alembic upgrade head` before the requested command.
  A normal container start/run can therefore migrate a database. Do not treat a
  default Compose invocation as read-only inspection.
- Creating/reviewing migration files is separate from permission to execute them.
  Do not run Alembic or Docker/Compose when the task forbids it. Local Alembic
  normally runs through Docker with sudo; neither tool is required to read files.
- Inspect the current revision chain and create a new revision for schema changes;
  do not rewrite released migrations. Review checks, defaults, foreign keys,
  indexes, data preservation and downgrade losses. Do not invent missing data to
  make a downgrade succeed.
- A migration file or Git tag is not evidence of applied database state. Do not
  assert a deployment or migration succeeded without authorized verification.
- Never execute `release.sh`, `update-main.sh`, or `rebuild.sh` as a harmless
  check. They can stop/start services, apply startup migrations, stage changes,
  commit, push or publish. Inspect their current behavior before authorized use.

## Documentation maintenance and approvals

- Update architecture for implemented behavior, decisions for confirmed choices
  and rationale, status for verified progress/defects/testing, and roadmap for
  pending requests/proposals. Label inferences and unresolved decisions clearly.
- Record source/revision and review date for baselines. Keep source implementation,
  tests, migration availability, migration application and deployment distinct.
- Preserve historical plans and explain superseding facts rather than silently
  deleting or rewriting project history. Keep relative links and file paths valid.
- Documentation-only work must not alter application code, migrations or runtime
  configuration. Report inconsistencies rather than expanding task scope.
- Do not commit, push, tag, publish, deploy, or change an external application
  without explicit authorization. Stop at the requested review boundary with a
  concrete diff/report; do not rerun permission questions for already authorized
  actions within the same scope.

## Release tooling

- Read `docs/RELEASE-WORKFLOW.md` before working on release tooling. The tracked
  `release.sh` / `schedule-release.sh` wrappers now call `tools/release/engine.py`;
  this supersedes the earlier description of release.sh as an ignored local script.
  `.release-config.json` remains ignored and must contain no credentials.
- Only `--dry-run` is a read-only release preview. Normal preparation can build
  disposable containers/create candidate commits; approval can push/tag/publish
  or install user timers. Never run these modes as harmless validation.
- Do not install active jobs or enable lingering without explicit authorization.
  Scheduled execution must use approved SHA/notes/saved runner, not moving main.
- Preserve candidate retention refs and Git tag reachability. Revalidation failure
  must stop publication, never substitute newer code or regenerate approved notes.
- Container success requires exact release workflow identity, OCI revision/version
  and receipt digest verification. Preserve serialized monotonic alias promotion;
  an older release must never overwrite newer `latest`/major-minor image aliases.
- Test publication with temporary repositories and mocks. Never use real GitHub
  mutations, application databases or installed timers as test fixtures.
