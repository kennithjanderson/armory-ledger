## Production migration and rollback procedure — planning only

No production operation is authorized by this checklist. Before a separately
approved release/deployment:

1. Review the two new migration files and the deployed revision. Confirm a single
   expected chain, image/source compatibility and the tested dev migration result.
2. Plan a maintenance/write-stop window and take a verified restorable PostgreSQL
   backup, retaining the previous image and configuration securely. Rehearse restore
   on a separately authorized disposable system. Record recovery acceptance checks.
3. After explicit production authorization, use the operator's verified deployment
   workflow. Container startup upgrades the schema before application startup;
   check migration output, current/head, health and private synthetic smoke tests.
4. On failure, stop writes and investigate before retrying. Do not blindly downgrade:
   the lot-merging downgrade refuses databases containing merges, retains enum
   labels, and dropping activity type loses classification. Never delete merge
   history to force downgrade. Prefer a reviewed forward fix or coordinated restore
   of the pre-upgrade backup and compatible previous image. A restore loses writes
   made since that backup; obtain operator approval for that recovery point.
5. Validate balances, preserved histories, ownership and scheduling after recovery.
   Reopen writes only after acceptance. Document the outcome without private data.

- [ ] Migration and recovery plan reviewed by operator; backup restore verified.
- [ ] All relevant automated and manual tests passed with results recorded.
- [ ] Documentation and dependency changes reviewed, no secrets in release diff.
- [ ] Remaining issues resolved or explicitly accepted before release approval.
- [ ] Explicit approval obtained for any future commit/tag/push/release/deployment.
