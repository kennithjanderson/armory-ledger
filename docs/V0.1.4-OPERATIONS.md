# v0.1.4 operations and recovery

Development implementation, reviewed 2026-10-17. This document describes the new
source; applying migrations, configuring persistent storage and deploying remain
separate operator actions. No production operation is authorized by these changes.

## Setup and privacy

The authoritative application version is `app/core/config.py`, now 0.1.4. The
new migration `d914b7ce203a` follows `c7d2a960e148`. It adds login-derived admin
membership, personal successful-backup preferences, system settings, events and
per-recipient notification/outbox state. Existing users start non-admin in the new
column and must sign in again. OIDC still requires Armory User plus Armory Admin;
there is no independently curated administrator mailing list. Role changes become
known on OIDC login, as before; local role revocation is checked on every privileged
request, notice read and queued delivery. No live identity-provider group polling
or provisioning was added.

Admin → Backup & Recovery deliberately grants **whole-instance recovery access**:
a downloaded archive contains all users' records and private audit history. This
is a stronger operational privilege than ordinary account administration. There
are still no inventory-browsing admin routes. Grant Armory Admin only to trusted
instance operators and protect downloaded archives as sensitive data.

Set `ARMORY_BACKUP_DIR` (default `/var/lib/armory/backups`) to the application's
private backup directory. Both Compose files mount host directory `./data/backups`
there; the local path is ignored by Git. Archives and the SQLite operations
catalogue survive application container recreation through this bind mount. Do not
delete or replace the host directory when rebuilding. POSIX locks and the catalogue
require a local filesystem with reliable flock/SQLite semantics; multiple hosts or
independent backup directories are not supported. The Docker image includes
PostgreSQL 17 client tools. Use PostgreSQL 17 for this tested recovery path.

The application container currently runs as root. The backup service creates the
directory with mode `0700`, the SQLite catalogue, lock and archive files with mode
`0600`, and plaintext staging files inside private `0700` temporary directories.
Protect the host `data/backups` directory from non-operators and monitor its free
space. Use the authenticated admin download for a separate off-host archive copy.

### Backup encryption key

`ARMORY_BACKUP_ENCRYPTION_KEY` is required for backup creation, archive import and
restore. Its exact format is canonical URL-safe base64, including padding, encoding
exactly 32 cryptographically random bytes. The service uses streaming AES-256-GCM:
each archive has a random 96-bit nonce and a 128-bit authentication tag. The key is
checked before database dumping starts. A missing or malformed key fails creation
closed. A wrong key or modified archive fails authentication before a restore
creates its pre-restore snapshot or changes the database. Downloads stream the
encrypted `.armorybackup` bytes unchanged. Completed files at rest are encrypted;
plaintext dumps and tar staging exist only in private temporary directories and
are removed after the operation, including ordinary failures.

Generate a new key only when preparing an installation, then configure the same
value for the application and store a protected copy in an off-host secret store
(for example, an organization password manager). A safe generator is:

```bash
python3 -c 'import base64,secrets; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode())'
```

Do not put the generated value in Git, a backup archive, ticket or chat. Do not
rotate it while archives encrypted with it must remain recoverable. There is no key
history or per-archive key selection: losing the key, or changing it, makes existing
archives permanently undecryptable. Restores must use the same key that encrypted
the source archive. Keep the key outside the application server as well as in the
protected runtime configuration. `ARMORY_SECRET_KEY` is a separate Fernet key for
SMTP credentials; it does not decrypt backup archives.

The development `.env` was checked without displaying any values. Its original
`ARMORY_BACKUP_ENCRYPTION_KEY` was malformed. With administrator authorization, it
was replaced on 2026-10-17 by a generated key matching the required format, then the
development environment was rebuilt and verified with encryption readiness. The
`.env` file is mode 0600. Keep a protected copy of this key outside the server; the
key value is not recorded in this document.

`ARMORY_TIMEZONE=UTC` is explicit; automatic backups initially remain disabled,
daily at 03:00, with 7 automatic archives retained. The admin form shows its IANA
zone. `ARMORY_WORKER_ENABLED=true` enables the five-second in-process worker loop;
POSIX worker and maintenance locks prevent concurrent operations across processes.
The leader processes durable jobs; ordinary requests retry with 503 during
maintenance. Backup status remains readable during creation. During database
restoration even status may return maintenance; the UI retries. Do not run direct
SQL writers while taking/restoring application snapshots.

## Archives and retention

The complete application PostgreSQL database is dumped with `pg_dump --format=custom`.
The current application has no persistent user-uploaded files; static images and
scripts are application code, supplied by the matching image. The archive contains
`database.dump`, `schedule.json`, and a format-1 manifest with UTC creation time,
application/schema versions, sizes and SHA-256 checksums. The dump includes account
records, inventory/history, email configuration (encrypted secret), notification
history, preferences and pending delivery records. Host secrets, `.env`, database
credentials, session keys, OIDC secrets, infrastructure and other backups are excluded.

The encrypted `.armorybackup` envelope contains an uncompressed tar payload with
bounded member count, names, types, metadata and total bytes. The default limit is
2 GiB (`ARMORY_BACKUP_MAX_BYTES`). AES-GCM authenticates contents; manifest checksums
also detect payload corruption after decryption. The v0.1.4 implementation
requires exact 0.1.4/schema compatibility; no older-version migration path is
claimed. Later development source discovers its schema heads from the included
Alembic migration tree rather than pinning one revision in backup code. That does
not add an automatic cross-version restore path.
Uploads use server UUIDs and never trust client filenames. Partial archives are not
usable. Completed archives are published by atomic rename and catalogued outside
the database; unknown valid orphan archives are imported, never automatic.

Types are stored in the persistent SQLite catalogue, not inferred from filenames:

- Automatic: retention may remove only older completed automatic archives after
  another automatic backup succeeds.
- Manual: Backup Now never runs retention and never removes an automatic archive.
- Pre-restore: always retained until explicit deletion.
- Imported: always retained until explicit deletion.

Retention 0 means unlimited. Negative/noninteger values are rejected. Failed backup
creation does not prune anything. Cleanup failure keeps the new backup successful
and produces a warning, not a contradictory backup failure. Jobs record sanitized
failures; deletion failure does not silently remove its catalogue entry. Jobs remain
for 90 days. Interrupted jobs are marked failed on the next leader pass. Missing
archive files are marked missing. The catalogue and encrypted archives survive
container recreation through the host bind mount. Local backups share the host's
failure domain; download copies to separate safeguarded storage.

Daily scheduling uses the first occurrence of a repeated DST wall time and skips a
nonexistent wall time. A restart with an overdue next-run time queues at most one
catch-up run, then computes the next future run. Changing settings recomputes next
run and never runs an unbounded catch-up loop.

## Recovery and failure handling

UI recovery requires typing `REPLACE ALL DATA`, displays archive date/version, and
validates integrity/compatibility before queueing. The worker revalidates under the
exclusive operation lock, creates and verifies a retained pre-restore archive, then
sets persistent maintenance. A failed pre-restore backup aborts without mutation.
`pg_restore --single-transaction --exit-on-error --clean --if-exists` restores the
DB. Schema/readiness is verified. If post-restore validation fails, the worker
restores the pre-restore dump; if that fails, maintenance stays enabled and the
catalogue records `offline_recovery_required` with the pre-restore ID. Never treat
that state as success.

A successful restore preserves the external archive catalogue and current schedule
configuration but **disables** automatic backups until reviewed. The archived
schedule is retained for reference, not silently activated. Pending historical
mail is cancelled, external pending notification work cleared and outbound work
paused during recovery. A changed session epoch forces a new OIDC login; restored
account identities must still match the configured provider. Preserve or reprovision
OIDC, database and session configuration separately.

Offline route (stop every application worker first; use only the intended instance):

```bash
# In a matching v0.1.4 application container with its DB configuration and backup
# volume mounted. Override the entrypoint: do not start migrations implicitly.
python -m app.recovery /var/lib/armory/backups/ARCHIVE_UUID.armorybackup --confirm-replace-all-data
```

Provision a clean database with the reviewed v0.1.4 migrations before recovery. The
same CLI also recovers a database left in maintenance. It uses the same archive
validation, locks, pre-restore protection, verification and rollback. For a corrupt
DB that cannot produce a pre-restore snapshot, preserve its database volume for
forensics and recover into a **new, clean migrated database**, then repoint the
instance after verification; do not bypass pre-restore protection on the damaged DB.
The external operational store must be available independently of the replaced DB.

## Email and notifications

Admin → Email configures enabled state (off initially), SMTP host/port, explicit
STARTTLS/implicit TLS/plain relay, bounded timeout, optional authentication,
From/Reply-To and a trusted public origin. TLS verifies certificates; no downgrade.
Choose plain only for a trusted local relay. Saving/booting never sends test email;
Send Test Email requires an explicit recipient and `SEND TEST` confirmation.
Diagnostics report SMTP acceptance, not inbox delivery, and do not disclose secrets.

SMTP passwords require `ARMORY_SECRET_KEY`, a Fernet key generated as shown in
`.env.example`. Keep that key **separately** from archives; losing it makes archived
passwords unusable. Passwords are masked in APIs; blank preserves, replacement
changes, explicit clear removes. Backup configuration includes ciphertext, not the
external key. On recovery with a missing/different key, replace or clear/reconfigure
the SMTP password before enabling successful delivery. Never put secrets in Git.

Initial event contract:

| Event | Severity | In-app | Email |
|---|---|---|---|
| Backup failure | Error/red | All known current admins | All known current admins when enabled |
| Backup cleanup failure | Warning/amber | All known current admins | All known current admins when enabled |
| Manual/automatic backup completed | Success/green | Personal opt-in, initially off | Separate personal opt-in, initially off |
| Newer GHCR `latest` image | Info/blue | All known current admins | All known current admins when enabled |

Pre-restore and import operations do not send completion events. Each administrator
can opt in to an in-app warning and/or email when a whole-instance restore is
initiated. The recipient preference and selected admin UUIDs are snapshotted into
the persistent external operations catalogue before PostgreSQL is replaced; after
the restore attempt or a successful rollback, the worker writes the notice into
the resulting database for recipients who remain admins. The warning says the
restore was initiated and points to Backup & Recovery for its final operation
status; it does not claim success. The external queue survives database replacement.
Email delivery uses the recovered database's current mail configuration, so an
email preference cannot deliver while SMTP is disabled after recovery.
Health checks do not emit alerts. Repeated unresolved cleanup failures form one
incident, increment occurrences and become unread again. Email sends once per
incident; a later successful
automatic cleanup resolves it and a new incident may alert again. Manual backups do
not resolve cleanup incidents. Event keys deduplicate retries. Durable external
failure work is retried when the application database returns. Failure to persist or
send a notice never changes an already successful backup result.

The in-process worker checks the public GHCR image
`ghcr.io/kennithjanderson/armory-ledger:latest` once per day. It reads the
`org.opencontainers.image.version` label from the `linux/amd64` manifest and compares
that version with the running application. It follows the mutable GHCR alias itself,
not GitHub release metadata, so a newer published release does not notify until the
`latest` image tag has actually been promoted. A newer image creates one admin-only
informational notice and queues email for administrators when system email is
enabled. The notice links to the local Changelog page. If the running version
catches up, or `latest` no longer points to a newer version, the notice is
resolved and removed from the unread bell; history follows the seven-day info
retention. A failed registry request creates no user notification and is retried
the next day. The read-only request reveals the host's network address to GHCR but
does not send account or inventory data. No container is pulled and no update is
installed automatically.

The bell is available to all authenticated users. Its endpoint returns only that
recipient's authorized records, bounded to 30 per page; the bell shows eight.
Polling every 30 seconds pauses in hidden tabs and backfills on reconnect/visibility.
Opening it does not mark notices read. Mark-one/all changes only that recipient;
removed admins lose system notices and pending system mail is cancelled. Semantic
severity borders and text labels are separate from unread outlines. Preferences
are personal and non-admins cannot subscribe to system notices.

SMTP runs in the worker, with a maximum 30-second timeout, at most three attempts,
exponential minute backoff and stable Message-ID. Permanent/configuration/TLS errors
are not silently retried forever. A crash between SMTP acceptance and DB commit can
still duplicate mail: exactly-once delivery is not promised. Disabled mail records
a disabled outcome rather than accumulating stale messages for later replay.
Missing addresses produce delivery diagnostics without losing bell notices.
History retention is severity-based: errors for 90 days, warnings for 30 days, and
info/success notices for 7 days from the latest event update. Unresolved errors and
warnings remain until resolved; pending/retrying email deliveries are kept. Read
status does not extend retention. This retention is independent of backup retention.
Future user-scoped events can reuse event/recipient/outbox records and safe local
actions; transfers, sharing and firearm-maintenance alerts are not shipped.

## Health and testing

The existing `/health` remains a fast DB readiness/version probe without sensitive
backup details. Detailed schema, storage writability/capacity, schedule/heartbeat,
last backup, cleanup and recovery state are administrator-only. Disabled scheduling
is informational. Health checks never create archives.

Automated synthetic tests use SQLite, temporary archive stores and mocked SMTP.
`tests/recovery_exercise.py` refuses to run without explicit disposable flags and a
specially named PostgreSQL database/host. It compares synthetic inventory and related
history across normal restore, failure after mutation and clean-install CLI recovery,
and checks pending-mail cancellation and catalogue persistence. It is not a tool for
operating on an existing development or production database.

Reference inspection: the requested Dispatcharr raw backup source URLs were not
accessible through the reference browser on 2026-10-16. Its GitHub repository lists
AGPL-3.0; Armory Ledger uses MIT. This implementation copies no Dispatcharr code.
