# v0.1.2 schema plan (not an executable migration)

No migration files have been created or executed for this work. Do not deploy
the new ORM code against the old schema: authenticated pages query announcements,
and firearm queries expect the new columns. Create, review, and apply the
migrations before starting this version of the application.

## Proposed revision chain

Existing head `ba5b6e5573c8` (accessory quantity)
→ `firearm_optional_serial_and_purchase_price` (revision ID to be assigned)
→ `scheduled_announcements` (revision ID to be assigned, new head).

These are revision descriptions, not allocated revision IDs. Existing migration
files are unchanged. There is no administration/purge migration in this scope.

## Firearms revision

- Alter `firearms.serial_number VARCHAR(255)` to permit NULL. Preserve existing
  values. New application writes normalize blank/whitespace to NULL.
- Add nullable `purchase_price NUMERIC(12,2)` without a default.
- Add nullable `purchase_currency VARCHAR(3)` without a default.
- Existing records have NULL in both new columns, not zero or an assumed price.
- Add `ck_firearms_purchase_price_nonnegative`:
  `purchase_price IS NULL OR purchase_price >= 0`.
- Add `ck_firearms_purchase_price_currency`: amount and currency must either
  both be NULL or both be non-NULL, with currency matching `^[A-Z]{3}$`.
- USD is the only currency written by the current application. There is no
  conversion, collection valuation, or total. A future UI can add currencies
  without relabeling existing recorded USD amounts.
- No ownership, manufacturer, caliber, or inventory foreign keys change.

Downgrade drops the two checks and price/currency columns, losing those values.
Reinstating serial-number NOT NULL must fail explicitly if NULL serial numbers
remain; do not fabricate serial numbers or discard firearms to make it succeed.

## Announcements revision

Create `announcements` with:

| Column | Definition |
| --- | --- |
| id | UUID primary key; application-generated UUID |
| title | VARCHAR(200), not null |
| message | TEXT, not null |
| severity | VARCHAR(20), not null; application default `info` |
| enabled | BOOLEAN, not null; server default true |
| starts_at | TIMESTAMP WITH TIME ZONE, not null; index |
| ends_at | TIMESTAMP WITH TIME ZONE, not null; index |
| created_by_user_id | UUID, not null; FK users.id |
| updated_by_user_id | UUID, not null; FK users.id |
| created_at | TIMESTAMP WITH TIME ZONE, not null; server default now() |
| updated_at | TIMESTAMP WITH TIME ZONE, not null; server default now() |

SQLAlchemy updates `updated_at` on application updates; it is not a database
trigger. Both user foreign keys use the default restrictive deletion behavior.

Checks:

- `ck_announcements_time_window`: ends_at > starts_at.
- `ck_announcements_severity`: info, success, warning, or danger.
- `ck_announcements_title`: trimmed title is nonempty.
- `ck_announcements_message`: trimmed message is nonempty and length <= 5000.

Application validation additionally strips text and rejects empty/whitespace
values, naive timestamps, numeric timestamps, and invalid schedule windows.
Accepted timestamps are normalized to UTC before storage. PostgreSQL TIMESTAMPTZ
stores instants; displayed timezone does not change the recorded instant.

Downgrade removes the indexes and table, losing announcements. No seed users,
instance-specific UUIDs, reference-data copies, or ownership migration are needed.

## Deferred purge contract

No purge buttons, routes, services, confirmation tables, or administrative audit
tables are implemented. Future inventory purge must also remove private inventory
audit events, whose JSON may contain private inventory details. It must retain
the local user, shared reference data, and a separate administrative audit record
without inventory details/counts. Self-purge is not supported initially.

## Validation before deployment

This iteration permits static/repository review only. Before deployment, validate
fresh and upgraded schemas against isolated PostgreSQL; exercise unauthorized
admin requests, account-only responses, ownership checks, announcement boundaries,
CSRF rejection, optional serial/price persistence and audit behavior. Do not use
the development or production database for destructive test fixtures.
