## 2. Standardize ammunition merge-history links

### Current issue

The Merge History section on ammunition detail pages displays source-lot links using default browser hyperlink styling, including purple visited-link coloring.

This is inconsistent with Armory Ledger's existing navy-and-cream visual design.

### Requirements

Inspect the application's existing link styles and reusable CSS classes.

Update the Merge History section to use the same visual treatment as other internal record links.

The links should:

- Use the site's existing link colors.
- Maintain consistent styling for visited, hover, and focus states.
- Remain visibly identifiable as interactive.
- Support keyboard navigation and visible focus indicators.
- Preserve their existing destinations and ownership checks.
- Avoid raw UUIDs as the primary user-facing link label.

Suggested link text:

"View source lot →"

The source-lot UUID may remain available as secondary metadata or through an existing expandable audit-details section.

Apply consistent styling to source and destination lot links where appropriate.

Do not change the underlying merge records or inventory accounting.

## 3. Timezone-aware announcement scheduling

### Current issue

Announcement scheduling requires administrators to manually convert local times into UTC.

This is inconvenient and error-prone, especially when Central Standard Time and Central Daylight Time have different UTC offsets.

### Design principle

**Store and compare timestamps in UTC; allow administrators to enter and view times in their chosen timezone.**

Use IANA timezone identifiers such as:

`America/Chicago`

Do not rely on fixed offsets such as UTC-6 because daylight saving time changes the offset.

### 3.1 Inspect existing implementation

Before coding, identify:

- Announcement model and timestamp columns.
- Announcement creation and editing routes.
- Scheduling form fields.
- Frontend JavaScript.
- Current UTC conversion behavior.
- Database column timezone semantics.
- How scheduled announcements become visible.
- How announcements are displayed to administrators and ordinary users.
- Existing tests.

Preserve existing scheduling semantics and access controls.

### 3.2 Timezone selection

Default the scheduling form to the browser's detected timezone.

Display the timezone clearly beside the scheduling fields.

Allow the administrator to select a different supported IANA timezone if practical within the existing UI.

At minimum, support `America/Chicago` and `UTC`, with a sensible way to handle other valid browser-detected timezones.

Do not infer timezone from server location.

### 3.3 Scheduling interface

Administrators should enter:

- Local publication date.
- Local publication time.
- Timezone.

The interface should show a readable UTC equivalent before saving.

Example:

Publication date: October 15, 2026

Publication time: 9:00 AM

Timezone: America/Chicago (CDT)

UTC equivalent: October 15, 2026, 14:00 UTC

The UTC preview must update when the date, time, or timezone changes.

Use existing form components and styling conventions.

Avoid introducing a large frontend dependency for a simple timezone conversion unless necessary.

### 3.4 Storage and validation

Preserve UTC as the canonical timestamp representation.

Server-side processing must validate and normalize the submitted schedule.

Do not trust a browser-supplied UTC conversion without validation.

Use an established timezone-aware conversion mechanism available in the project's existing stack.

If additional dependencies are required, explain why and keep them minimal.

Inspect whether the existing database uses timezone-aware or naive UTC timestamps and preserve its established convention unless a safe, explicitly justified change is required.

Do not silently reinterpret existing timestamps.

### 3.5 Daylight saving time

Handle daylight saving time correctly.

Specifically test:

- Central Standard Time (UTC-6).
- Central Daylight Time (UTC-5).
- Spring-forward nonexistent local times.
- Fall-back ambiguous local times.

For nonexistent local times, display a validation error and require another time.

For ambiguous local times, require an explicit choice of occurrence or otherwise provide an unambiguous, documented resolution. Do not silently choose the wrong occurrence.

### 3.6 Editing existing announcements

When editing an existing announcement:

- Load the stored UTC timestamp.
- Convert it to the selected timezone for display.
- Preserve the original instant if the administrator saves without changing the schedule.
- Convert edited local values back to UTC.
- Prevent repeated timezone conversions from shifting the scheduled instant.

Existing announcement timestamps must remain unchanged by any migration or deployment.

### 3.7 Announcement visibility

Preserve the current rules governing when scheduled announcements become visible.

Verify that visibility checks compare compatible UTC instants and do not depend on the server's local timezone.

Do not modify unrelated announcement publication, expiration, or dismissal behavior.

If the system has both start and end times, apply consistent timezone handling to both.
